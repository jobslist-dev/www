Wie man eine Take-Home-Aufgabe gestaltet, die Kandidaten nicht verübeln

Das JobsList.dev-Team·30. Juni 2026·5 Min. Lesezeit

Take-Home-Aufgaben sind die umstrittenste Phase im technischen Recruiting. Gut gemacht, liefern sie besseres Signal als jedes Gespräch: echter Code, so geschrieben, wie der Kandidat tatsächlich arbeitet, an einem Problem, das der Stelle ähnelt. Schlecht gemacht, sind sie ein unbezahltes Wochenende, das stillschweigend jeden Kandidaten mit Alternativen aussortiert – also genau die Kandidaten, die Sie am meisten wollen.

Der Unterschied liegt fast ausschließlich in der Gestaltung.

Entscheiden Sie, ob Sie überhaupt eine brauchen

Bevor Sie irgendetwas entwerfen, prüfen Sie, ob eine Take-Home-Aufgabe das richtige Instrument ist. Sie passt gut, wenn:

  • Die Rolle umfangreiche eigenständige Arbeit umfasst, die Sie in einem Gespräch nicht beobachten können.
  • Sie echten Code sehen wollen – Struktur, Benennung, Tests, Commits – statt Whiteboard-Ergebnisse.
  • Zu Ihren Kandidaten Menschen gehören, die im Gespräch schlecht abschneiden, aber hervorragend arbeiten – eine große Gruppe.

Sie passt schlecht, wenn Sie stattdessen neunzig Minuten mit ihnen pairen könnten und dabei dasselbe lernen und zugleich sehen, wie sie zusammenarbeiten. Pairing ist für Sie schneller, für die Kandidaten weniger aufwendig und liefert oft mehr Signal. Ziehen Sie es zuerst in Betracht und bieten Sie es als Alternative an, selbst wenn Sie Take-Home-Aufgaben einsetzen – manche Kandidaten bevorzugen deutlich das eine oder das andere.

Die Regeln, die Kandidaten in Ihrem Prozess halten

Begrenzen Sie sie auf drei Stunden – und meinen Sie es ernst

Nennen Sie das Zeitlimit und gestalten Sie dann etwas, das eine kompetente Person tatsächlich darin schafft. Der häufige Fehler ist eine Aufgabe, die mit "etwa drei Stunden" angekündigt wird und realistisch acht dauert. Kandidaten merken das, und es beschädigt das Vertrauen, noch bevor Sie sich getroffen haben.

Testen Sie Ihre eigene Aufgabe: Lassen Sie zwei Ingenieure aus Ihrem Team sie ohne Vorbereitung bearbeiten und stoppen Sie ehrlich die Zeit. Gestalten Sie dann für die langsamere Person.

Begrenzen Sie auch, was Sie bewerten

Sagen Sie den Kandidaten explizit, was Sie bewerten und was nicht. "Wir schauen darauf, wie Sie den Code strukturieren und mit Fehlern umgehen. Bauen Sie keine Authentifizierung, gestalten Sie kein Styling, deployen Sie es nicht." Ohne das übertreiben es gewissenhafte Kandidaten mit Feinschliff – sie wenden neun Stunden auf, weil sie nicht erkennen können, worauf es ankommt – und Sie haben nach Freizeit statt nach Fähigkeit selektiert.

Bezahlen Sie für alles Substanzielle

Wenn die Aufgabe mehr als etwa zwei Stunden dauert, bezahlen Sie dafür. Ein bescheidenes Honorar verändert die Dynamik völlig: Es signalisiert, dass Sie ihre Zeit schätzen, macht eine ausgedehnte Aufgabe vertretbar und verbessert die Abschlussquoten unter Senior-Kandidaten deutlich.

Es zwingt auch Ihnen eine nützliche Disziplin auf. Teams, die für Take-Home-Aufgaben zahlen, gestalten kürzere.

Lassen Sie sie der echten Arbeit ähneln

Die besten Aufgaben sind kleine Versionen echter Arbeit: eine bestehende kleine Codebasis erweitern, einen Bug in unbekanntem Code beheben, einen kleinen Endpoint gegen eine echte API bauen oder einen Pull Request reviewen und kommentieren.

Letzteres wird zu selten genutzt und ist hervorragend. Es dauert vierzig Minuten, lässt sich nicht überzeugend auslagern und zeigt Ihnen, wie jemand über den Code anderer denkt – was den Großteil dessen ausmacht, was Ingenieure tatsächlich tun.

Vermeiden Sie abstrakte Rätsel ohne Bezug zu Ihrem Produkt. Sie messen Rätselübung.

Lassen Sie sie ihre echten Werkzeuge nutzen

Kandidaten arbeiten mit KI-Assistenten, Dokumentation und ihrem gewohnten Editor-Setup. Aufgaben, die etwas anderes vorgeben, testen Gehorsam, nicht Fähigkeit.

Gestalten Sie stattdessen darum herum: Im Folgegespräch findet die eigentliche Bewertung statt. Bitten Sie sie, eine Entscheidung durchzugehen, ändern Sie live eine Anforderung oder lassen Sie sie einen Trade-off erklären. Wer seine Abgabe wirklich versteht, meistert das mühelos; wer nicht, fällt innerhalb von Minuten auf. Das ist ein besserer Filter als jede Vertrauensregel und beleidigt nicht die Menschen, die sich an die Regeln halten.

Besprechen Sie sie immer live

Bewerten Sie eine Abgabe niemals isoliert. Ein dreißigminütiges Gespräch über ihren Code fügt enormes Signal hinzu: Warum diese Struktur, was würden Sie mit einem weiteren Tag ändern, wie würden Sie die zehnfache Last bewältigen, wo halten Sie das für am schwächsten?

Es schützt Kandidaten auch davor, wegen eines Missverständnisses abgelehnt zu werden. Und es ist die Phase, in der der Unterschied zwischen tiefem Verständnis und oberflächlichem Zusammenbau unverkennbar wird.

Was Sie bewerten – und wie

Schreiben Sie Ihre Kriterien auf, bevor Sie eine einzige Abgabe sehen, und bewerten Sie jeden Kandidaten anhand derselben Liste. Sonst rationalisieren Sie eine Präferenz, die Sie in den ersten dreißig Sekunden gebildet haben.

Sinnvolle Kriterien für die meisten Rollen:

  • Funktioniert es? Erfüllt die genannten Anforderungen.
  • Ist es lesbar? Benennung, Struktur und ob jemand anderes es warten könnte.
  • Ist es angemessen getestet? Urteilsvermögen darüber, was einen Test verdient, nicht rohe Abdeckung.
  • Wie geht es mit Fehlern um? Fehler, Randfälle, ungültige Eingaben.
  • Haben sie sich an die Vorgabe gehalten – einschließlich der Anweisung, es nicht mit Feinschliff zu übertreiben?
  • Ist die README klar? Annahmen, Trade-offs, was sie mit mehr Zeit täten.

Der letzte Punkt verdient hohes Gewicht. Ein Kandidat, der seine Annahmen dokumentiert und die eigenen Abkürzungen benennt, zeigt Ihnen genau das Urteilsvermögen, für das Sie einstellen.

Fehler, die Sie gute Kandidaten kosten

  • Kein genanntes Zeitlimit. Kandidaten nehmen an, mehr sei besser, und verübeln jede Stunde.
  • Vage Anforderungen, die sie zwingen, den Umfang zu erraten.
  • Etwas bauen lassen, das Sie verwenden. Schon der Anschein von Gratisarbeit vergiftet den Prozess. Verlangen Sie niemals Arbeit, die Ihr echtes Produkt berührt.
  • Sie zu früh verschicken. Eine Take-Home-Aufgabe vor jedem menschlichen Gespräch verlangt Stunden von jemandem, der noch nicht weiß, ob er die Stelle will. Platzieren Sie sie nach dem Kennenlerngespräch.
  • Langsames Feedback. Zwei Wochen auf einer Abgabe zu sitzen, nachdem man drei Stunden unbezahlte Arbeit verlangt hat, ist die häufigste Beschwerde von Kandidaten – und liegt vollständig in Ihrer Hand.
  • Ablehnung ohne Feedback. Sie haben Ihnen Stunden gegeben. Geben Sie ihnen zwei konkrete Sätze.
  • Keine Alternative angeboten. Kandidaten mit Betreuungspflichten oder einem fordernden aktuellen Job werden durch Take-Home-Aufgaben überproportional ausgeschlossen. Das Angebot einer Live-Pairing-Option hält sie im Prozess.

Das Fazit

Eine Take-Home-Aufgabe ist eine Bitte um die Abende eines Menschen. Behandeln Sie sie so: Begrenzen Sie sie auf drei Stunden, sagen Sie genau, was Sie bewerten, bezahlen Sie für alles Längere, stützen Sie sie auf echte Arbeit, lassen Sie die Leute ihre echten Werkzeuge nutzen und besprechen Sie sie immer live. Bieten Sie Pairing als Alternative an und liefern Sie Ergebnisse innerhalb von Tagen. Richtig gemacht ist sie die aussagekräftigste Phase, die Sie durchführen – nachlässig gemacht ist sie ein stiller Filter, der Ihre stärksten Kandidaten aussortiert.
