e:T2039,<p>Take-Home-Aufgaben sind die umstrittenste Phase im technischen Recruiting. Gut gemacht, liefern sie besseres Signal als jedes Gespräch: echter Code, so geschrieben, wie der Kandidat tatsächlich arbeitet, an einem Problem, das der Stelle ähnelt. Schlecht gemacht, sind sie ein unbezahltes Wochenende, das stillschweigend jeden Kandidaten mit Alternativen aussortiert – also genau die Kandidaten, die Sie am meisten wollen.</p>
<p>Der Unterschied liegt fast ausschließlich in der Gestaltung.</p>
<h2>Entscheiden Sie, ob Sie überhaupt eine brauchen</h2>
<p>Bevor Sie irgendetwas entwerfen, prüfen Sie, ob eine Take-Home-Aufgabe das richtige Instrument ist. Sie passt gut, wenn:</p>
<ul>
<li>Die Rolle umfangreiche eigenständige Arbeit umfasst, die Sie in einem Gespräch nicht beobachten können.</li>
<li>Sie echten Code sehen wollen – Struktur, Benennung, Tests, Commits – statt Whiteboard-Ergebnisse.</li>
<li>Zu Ihren Kandidaten Menschen gehören, die im Gespräch schlecht abschneiden, aber hervorragend arbeiten – eine große Gruppe.</li>
</ul>
<p>Sie passt schlecht, wenn Sie stattdessen neunzig Minuten mit ihnen pairen könnten und dabei dasselbe lernen und zugleich sehen, wie sie zusammenarbeiten. Pairing ist für Sie schneller, für die Kandidaten weniger aufwendig und liefert oft mehr Signal. Ziehen Sie es zuerst in Betracht und bieten Sie es als Alternative an, selbst wenn Sie Take-Home-Aufgaben einsetzen – manche Kandidaten bevorzugen deutlich das eine oder das andere.</p>
<h2>Die Regeln, die Kandidaten in Ihrem Prozess halten</h2>
<h3>Begrenzen Sie sie auf drei Stunden – und meinen Sie es ernst</h3>
<p>Nennen Sie das Zeitlimit und gestalten Sie dann etwas, das eine kompetente Person tatsächlich darin schafft. Der häufige Fehler ist eine Aufgabe, die mit &quot;etwa drei Stunden&quot; angekündigt wird und realistisch acht dauert. Kandidaten merken das, und es beschädigt das Vertrauen, noch bevor Sie sich getroffen haben.</p>
<p>Testen Sie Ihre eigene Aufgabe: Lassen Sie zwei Ingenieure aus Ihrem Team sie ohne Vorbereitung bearbeiten und stoppen Sie ehrlich die Zeit. Gestalten Sie dann für die langsamere Person.</p>
<h3>Begrenzen Sie auch, was Sie bewerten</h3>
<p>Sagen Sie den Kandidaten explizit, was Sie bewerten und was nicht. &quot;Wir schauen darauf, wie Sie den Code strukturieren und mit Fehlern umgehen. Bauen Sie keine Authentifizierung, gestalten Sie kein Styling, deployen Sie es nicht.&quot; Ohne das übertreiben es gewissenhafte Kandidaten mit Feinschliff – sie wenden neun Stunden auf, weil sie nicht erkennen können, worauf es ankommt – und Sie haben nach Freizeit statt nach Fähigkeit selektiert.</p>
<h3>Bezahlen Sie für alles Substanzielle</h3>
<p>Wenn die Aufgabe mehr als etwa zwei Stunden dauert, bezahlen Sie dafür. Ein bescheidenes Honorar verändert die Dynamik völlig: Es signalisiert, dass Sie ihre Zeit schätzen, macht eine ausgedehnte Aufgabe vertretbar und verbessert die Abschlussquoten unter Senior-Kandidaten deutlich.</p>
<p>Es zwingt auch Ihnen eine nützliche Disziplin auf. Teams, die für Take-Home-Aufgaben zahlen, gestalten kürzere.</p>
<h3>Lassen Sie sie der echten Arbeit ähneln</h3>
<p>Die besten Aufgaben sind kleine Versionen echter Arbeit: eine bestehende kleine Codebasis erweitern, einen Bug in unbekanntem Code beheben, einen kleinen Endpoint gegen eine echte API bauen oder einen Pull Request reviewen und kommentieren.</p>
<p>Letzteres wird zu selten genutzt und ist hervorragend. Es dauert vierzig Minuten, lässt sich nicht überzeugend auslagern und zeigt Ihnen, wie jemand über den Code anderer denkt – was den Großteil dessen ausmacht, was Ingenieure tatsächlich tun.</p>
<p>Vermeiden Sie abstrakte Rätsel ohne Bezug zu Ihrem Produkt. Sie messen Rätselübung.</p>
<h3>Lassen Sie sie ihre echten Werkzeuge nutzen</h3>
<p>Kandidaten arbeiten mit KI-Assistenten, Dokumentation und ihrem gewohnten Editor-Setup. Aufgaben, die etwas anderes vorgeben, testen Gehorsam, nicht Fähigkeit.</p>
<p>Gestalten Sie stattdessen darum herum: Im Folgegespräch findet die eigentliche Bewertung statt. Bitten Sie sie, eine Entscheidung durchzugehen, ändern Sie live eine Anforderung oder lassen Sie sie einen Trade-off erklären. Wer seine Abgabe wirklich versteht, meistert das mühelos; wer nicht, fällt innerhalb von Minuten auf. Das ist ein besserer Filter als jede Vertrauensregel und beleidigt nicht die Menschen, die sich an die Regeln halten.</p>
<h3>Besprechen Sie sie immer live</h3>
<p>Bewerten Sie eine Abgabe niemals isoliert. Ein dreißigminütiges Gespräch über ihren Code fügt enormes Signal hinzu: Warum diese Struktur, was würden Sie mit einem weiteren Tag ändern, wie würden Sie die zehnfache Last bewältigen, wo halten Sie das für am schwächsten?</p>
<p>Es schützt Kandidaten auch davor, wegen eines Missverständnisses abgelehnt zu werden. Und es ist die Phase, in der der Unterschied zwischen tiefem Verständnis und oberflächlichem Zusammenbau unverkennbar wird.</p>
<h2>Was Sie bewerten – und wie</h2>
<p>Schreiben Sie Ihre Kriterien auf, bevor Sie eine einzige Abgabe sehen, und bewerten Sie jeden Kandidaten anhand derselben Liste. Sonst rationalisieren Sie eine Präferenz, die Sie in den ersten dreißig Sekunden gebildet haben.</p>
<p>Sinnvolle Kriterien für die meisten Rollen:</p>
<ul>
<li><strong>Funktioniert es?</strong> Erfüllt die genannten Anforderungen.</li>
<li><strong>Ist es lesbar?</strong> Benennung, Struktur und ob jemand anderes es warten könnte.</li>
<li><strong>Ist es angemessen getestet?</strong> Urteilsvermögen darüber, was einen Test verdient, nicht rohe Abdeckung.</li>
<li><strong>Wie geht es mit Fehlern um?</strong> Fehler, Randfälle, ungültige Eingaben.</li>
<li><strong>Haben sie sich an die Vorgabe gehalten</strong> – einschließlich der Anweisung, es nicht mit Feinschliff zu übertreiben?</li>
<li><strong>Ist die README klar?</strong> Annahmen, Trade-offs, was sie mit mehr Zeit täten.</li>
</ul>
<p>Der letzte Punkt verdient hohes Gewicht. Ein Kandidat, der seine Annahmen dokumentiert und die eigenen Abkürzungen benennt, zeigt Ihnen genau das Urteilsvermögen, für das Sie einstellen.</p>
<h2>Fehler, die Sie gute Kandidaten kosten</h2>
<ul>
<li><strong>Kein genanntes Zeitlimit.</strong> Kandidaten nehmen an, mehr sei besser, und verübeln jede Stunde.</li>
<li><strong>Vage Anforderungen</strong>, die sie zwingen, den Umfang zu erraten.</li>
<li><strong>Etwas bauen lassen, das Sie verwenden.</strong> Schon der Anschein von Gratisarbeit vergiftet den Prozess. Verlangen Sie niemals Arbeit, die Ihr echtes Produkt berührt.</li>
<li><strong>Sie zu früh verschicken.</strong> Eine Take-Home-Aufgabe vor jedem menschlichen Gespräch verlangt Stunden von jemandem, der noch nicht weiß, ob er die Stelle will. Platzieren Sie sie nach dem Kennenlerngespräch.</li>
<li><strong>Langsames Feedback.</strong> Zwei Wochen auf einer Abgabe zu sitzen, nachdem man drei Stunden unbezahlte Arbeit verlangt hat, ist die häufigste Beschwerde von Kandidaten – und liegt vollständig in Ihrer Hand.</li>
<li><strong>Ablehnung ohne Feedback.</strong> Sie haben Ihnen Stunden gegeben. Geben Sie ihnen zwei konkrete Sätze.</li>
<li><strong>Keine Alternative angeboten.</strong> Kandidaten mit Betreuungspflichten oder einem fordernden aktuellen Job werden durch Take-Home-Aufgaben überproportional ausgeschlossen. Das Angebot einer Live-Pairing-Option hält sie im Prozess.</li>
</ul>
<h2>Das Fazit</h2>
<p>Eine Take-Home-Aufgabe ist eine Bitte um die Abende eines Menschen. Behandeln Sie sie so: Begrenzen Sie sie auf drei Stunden, sagen Sie genau, was Sie bewerten, bezahlen Sie für alles Längere, stützen Sie sie auf echte Arbeit, lassen Sie die Leute ihre echten Werkzeuge nutzen und besprechen Sie sie immer live. Bieten Sie Pairing als Alternative an und liefern Sie Ergebnisse innerhalb von Tagen. Richtig gemacht ist sie die aussagekräftigste Phase, die Sie durchführen – nachlässig gemacht ist sie ein stiller Filter, der Ihre stärksten Kandidaten aussortiert.</p>
